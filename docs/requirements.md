# Requirements

## How to use this document

Record requirements the team and supervisor have agreed on. Mark each item with an identifier and status; do not present proposals as approved requirements.

## Functional requirements

Document expected behavior for:

- Calculating energy from power, usage time, and quantity.
- Showing daily and 30-day estimates.
- Accepting a user-entered tariff before estimating cost.
- Searching, filtering, and sorting appliance records.
- Displaying energy-saving tips with relevant categories.
- Any optional local storage behavior, including what is stored and how users can clear it.

## Non-functional requirements

Specify accessibility, responsive behavior, usability, browser support, performance, privacy, and static-hosting expectations.

## Data requirements

Define appliance and tip fields, units, validation rules, provenance, update responsibility, and treatment of unknown values. Appliance ratings must be identified as illustrative until verified.

## Constraints and exclusions

The starter uses HTML5, CSS3, vanilla JavaScript, and static JSON. It has no backend, database, authentication, or frontend framework.

## Acceptance criteria and traceability

Add testable acceptance criteria and link each requirement to a test case in `testing-documentation.md`. Include owner and status columns as the team agrees.
